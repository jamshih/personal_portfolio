WRONGBOOK / IOS / PRIVATE REPO

WrongBook

While preparing for the GSAT, I kept doing questions I had already gotten wrong because I almost never revisited them properly. I thought it would be better if I could just build an app for that.

First version
Upload a photo of a question, add a few details, and log it. That was basically the product.
Built by me
Basically everything: iOS app, backend, AI pipeline, product design, subscriptions, deployment, and the debugging around all of it.
Hardest work
OCR, math notation, diagram extraction, sync, reliability, and making the scanner behave consistently.
Stack
Swift · Vision · Supabase · StoreKit · Edge Functions
I keep the source private while I work toward release.
NOTES FROM BUILDING IT
The scanner is the part I’m proudest of.

I put days into OCR and diagram extraction. The useful lesson was that “worked once” and “works reliably” are completely different standards.

503s and inconsistent results made this obvious.
I started caring about logging because guessing is awful.

When failures felt random, I needed enough diagnostics to see what actually happened instead of poking at the app until the bug disappeared.

I didn’t want the app to look AI-generated.

The early UI kept coming back as white backgrounds, blue text, and generic components. I spent much more time on animation, custom assets, the subject map, and the question page than an MVP strictly needed.

SEARCHRECALL / WEB + EXTENSION / LIVE

SearchRecall

I would search an English word, understand it for a moment, and then never touch it again. If I was lucky I would see it later. If not, it might show up on a test and I’d think, “Darn it, I wish I had remembered that.”

First version
A Chrome extension that sent my history to Gemini and asked which entries were English vocabulary searches.
What it became
A learning workflow that turns supported searches and dictionary lookups into vocabulary records and review.
Scale tested
Chrome History / Takeout imports with 100k+ records.
Built by me
Web app, Chrome Helper, history processing, AI flow, backend, product design, and iteration after iteration.
Open search-recall.com ↗
Private codebase. The product itself is live.
WHY IT EXISTS
Search → forget → see it on a test.

I didn’t need another dictionary. I wanted the words I had already looked up to come back on purpose instead of depending on luck.

The product grew from my own usage.

The first version was simple. I kept adding features when I noticed what was missing rather than starting from a giant product plan.

I build this way a lot.

I notice something inefficient in my own life, make the smallest thing that might help, then keep iterating if I still care about the problem.

02 / Field notes

Things I learned by doing this badly first.

AI + taste

At first I was amazed that AI could build anything. After seeing enough generic output, I started noticing immediately when something felt off.

AI makes the MVP easier. A curated product still comes from someone deciding what is worth keeping, changing, or throwing away.
Design workflow

“Implement this mockup” was not enough.

I browse Pinterest for references, analyze the style into a style guide, generate the mockup, ask another agent to list every asset in it, create those assets separately, then hand the full package to coding agents. That gets me much closer to the mockup than asking for code in one shot.
Agent workflow

I used to tell AI “fix this, fix that” and force changes into main.

Now I write a contract for bigger changes, use stronger models for planning and review, let agents challenge each other when they disagree, use cheaper models for implementation, validate on branches, smoke-test on a physical device, then merge.
Using models

I pay much more attention to context windows, token usage, and which model should do which job.

The model is part of the engineering choice now. I don’t want to spend expensive reasoning on mechanical work, and I don’t want a weaker model making architecture decisions just because it is available.
Starting

You can be preparing to do something big and still just start building.

A laptop and an AI-agent subscription are enough to try much more than they used to be. I would rather start with a fragile version and learn from it than wait until I feel ready for the whole thing.
Why I keep building

Because I love it and it’s fun.

Software is just an entry point for me. I want to build more than software eventually. Some ideas are still staying private.
03 / Process changed

I’m still learning software engineering while shipping real software.

A year ago I barely understood why PRs and branches mattered. Now I’m much more careful about how a change reaches main.

01
Write the change down first

For larger work, I define the contract, constraints, and what counts as done before implementation starts.

02
Separate planning from implementation

I use stronger models for architecture and review, then cheaper models for the mechanical work when that is enough.

03
Make disagreement useful

If two agents reach different conclusions, I want the conflict surfaced and argued through instead of silently picking one answer.

04
Validate before main

Branches, builds, logs, and physical-device smoke tests matter because a clean-looking diff does not prove the product works.
